Content Opportunity Scoring for Search Performance Review

Using observable webpage search and engagement signals to prioritize content-review opportunities through a leakage-audited machine learning workflow.

FlyRank ML Internship — Machine Learning Track

Abstract

Content teams often need to decide which webpages should be reviewed first, but large-scale search-performance data makes manual prioritization difficult. This project investigates whether observable webpage performance signals can support a ranked content-review workflow using production-style search and analytics data from the FlyRank ML Internship dataset.

We aggregate webpage-level performance signals, apply leakage checks, compare a transparent rule-based baseline with a learned Logistic Regression model, and evaluate the model using grouped validation that prevents client overlap between training and validation data.

The learned model achieved an F1 score of 0.795, compared with 0.535 for the Week-4 transparent baseline on the same modeling task.

The resulting system is intended as decision support for human SEO/content review, not as a causal model of whether refreshing a page will improve search performance.

1. Question

Research Question

Can observable webpage search and engagement signals be used to prioritize webpages for content review?

The goal is to help an SEO/content team decide which webpages should be reviewed first when working with a large number of webpages.

REVIEW Highest priority for human review.
WATCH Monitor for a potential opportunity.
NO_ACTION No immediate priority from the current rule.

The unit of analysis is an individual webpage identified using pseudonymized client and content identifiers.

The system is designed as decision support, not as an autonomous content-editing system.

3. Methodology

Features

The final leakage-audited model feature set consists of:

  • impressions
  • clicks
  • avg_position
  • pageviews
  • sessions
  • users

Target

The modeling task predicts whether a webpage experiences a future decline relative to its current observed performance.

Current / historical features → Decision point → Future outcome → Target

Separating the feature window from the future outcome is important for avoiding target leakage.

Model

The learned model is Logistic Regression. It was selected because it is simple, computationally efficient, suitable for binary classification, and relatively easy to interpret.

Transparent Baseline

Condition Score Reason Action
High impressions + low CTR 2 LOW_CTR_HIGH_VOLUME REVIEW
High impressions 1 HIGH_SEARCH_VOLUME WATCH
Otherwise 0 LOW_PRIORITY NO_ACTION

Validation

Grouped validation based on client_hash_id prevents the same client from appearing in both the training and validation groups.

Evaluation

The primary metric is F1 score, with accuracy, precision, recall, and ROC-AUC also reported.

Leakage Audit

PASS — no known target/flag/future fields are in the feature list.

5. Limitations

Observational Data

The dataset contains observed search and engagement behavior rather than randomized experimental data. Therefore, the analysis does not establish causality.

Limited Time Window

The development analysis uses a defined period. Search behavior can change across time, industries, seasons, and external events.

Client Differences

Clients can differ in site structure, audience, content strategy, industry, and search behavior. Grouped validation reduces client overlap but does not guarantee performance on every unseen client.

Feature Limitations

The model does not directly understand search intent, content quality, competitor content, SERP features, title quality, internal linking, backlinks, or business priorities.

Target Limitation

The decline target is an operational outcome definition rather than a direct measurement of content quality.

Honest claim: The workflow can rank observed webpage-performance patterns for content-review prioritization, and the learned model outperformed the transparent baseline on F1 in the evaluated development setting.

It does not prove which webpages should definitely be refreshed, predict Google's ranking algorithm, or guarantee improved performance after a content change.

6. Ranked Recommendations

Priority 1 — REVIEW

Reason code: LOW_CTR_HIGH_VOLUME

Pages with substantial search exposure and relatively low CTR receive the highest priority for human investigation.

Reviewers should examine search intent, ranking position, SERP context, title/snippet relevance, content freshness, query mix, recent changes, business relevance, and expected effort versus potential value.

Priority 2 — WATCH

Reason code: HIGH_SEARCH_VOLUME

Pages with meaningful search exposure but without the stronger low-CTR condition can be monitored for future changes.

Priority 3 — NO_ACTION

Reason code: LOW_PRIORITY

Pages that do not meet the current priority conditions receive no immediate recommendation from this baseline.

Human-in-the-loop principle: The system recommends where to look, not what to publish.

Failure Cases

High-volume page with low CTR

Low CTR can result from SERP layout, search intent, query mix, or user behavior. It does not by itself prove that content needs refreshing.

Low-ranking page

A page with low CTR and poor average position may be prioritized, but its low CTR may primarily reflect its ranking position rather than content quality.

Future decline not captured

Competitor activity, seasonality, changes in search demand, external events, or other ranking-environment changes may cause future decline without being represented in the current feature set.

False positives and false negatives

The model may prioritize pages that remain stable or miss pages that later decline. These errors reinforce the need for continued validation and human review.

Conclusion

This project investigated whether observable webpage performance signals could support content-review prioritization.

The analysis established a workflow from data-contract definition and leakage auditing through signal analysis, transparent baseline scoring, learned modeling, validation, and action-playbook generation.

The Logistic Regression model achieved an F1 score of 0.795, compared with 0.535 for the transparent Week-4 baseline in the development evaluation.

The practical contribution is therefore a human-in-the-loop prioritization workflow: measurable signals help decide where SEO/content teams should investigate first, while expert review determines whether any action is appropriate.

Future work should test the workflow on additional time periods, unseen clients, richer content and SERP features, and prospective outcomes after human-reviewed content changes.
